# データ設計

検索・表示の単位は**ページ**、出典と登録の単位は**資料**とする。ページは人間向け画面とエージェントに共通の資産として扱う。APIのJSONでは以下の名前を使う。

| 単位 | 主な項目 | 説明 |
| --- | --- | --- |
| 資料 `Document` | `id`, `title`, `authors[]`, `fileName`, `format`, `folderPath[]`。追加予定: `category`, `presentationYear`, `origin` | 元ファイルと全ページに共通する情報 |
| ページ `Page` | `id`, `documentId`, `pageNumber`, `heading`, `summary`, `tags[]`, `previewUrl`。追加予定: `slideRole` | 検索結果・詳細表示の単位。API応答では `document` に資料情報も含める |

`Document.id` は登録したPDF/PPTXの資料全体のID、`Page.id` は1ページのIDとする。どちらもファイル名やページ番号から作らない安定した識別子とする。`Page.documentId` で資料全体に紐づけ、`pageNumber` はその資料内で1始まりとする。`format` は `pdf` または `pptx`。著者が不明なら空配列、見出し・概要が不明なら空文字列を使う。著者は資料に、役割を表すタグはページに付ける。著者フィルタは `authors[]` 内の名前との完全一致で資料に属するページを絞り込む。

ページは `documentId` で資料に紐づく。APIの `Page` 応答には、資料情報を `document` として含め、`document.id` と `documentId` を一致させる。一覧・検索では候補選択用の `PageSummary` を返す。取込直後のページのタグは空配列とし、後からページ単位で付与・修正する。

メタデータは用途に応じて次の3種類に整理する。

| 種類 | 主な情報 | 用途 |
| --- | --- | --- |
| 基本情報 | ID、ページ番号、見出し、概要、タグ、プレビュー、資料タイトル・著者・元フォルダ | 一覧・検索・詳細表示 |
| 意味・表現情報 | 発表内での役割、説明の流れ、内容・図の種類、レイアウト、強調点 | 詳細な検索、エージェントによる参考例の選択 |
| 技術情報 | 元ファイル、抽出文字列・図形情報、Embedding、解析モデルと版 | 取込処理、検索処理、高度な参照 |

Embeddingは検索の内部処理に用い、生ベクトルは通常の検索・詳細APIで返さない。元ファイルは資料に紐づき、プレビューはページに紐づく。

`folderPath` は `['論文読み会', '2025']` のように上位から並ぶ表示用の出典情報である。フォルダ階層による絞り込みに使うが、フォルダ名をページのタグへ自動変換しない。Drive連携時は同名フォルダを区別できるよう、フォルダのIDも別に保持する。

初期の資料一覧は取得済みのページを `documentId` でまとめて構成する。資料詳細では `GET /api/documents/{documentId}/pages` で全ページを `pageNumber` 順に取得する。ページ数はそのAPIの `total` を使い、代表画像には既存ページのプレビューを参照する。

## 検索用メタデータ（追加予定・Issue #39）

| 項目 | 所属 | 値 | 扱い |
| --- | --- | --- | --- |
| `category` | 資料 | `paper_reading`, `research_presentation`, `other`, `null` | 資料区分。学会名などの固有名は元フォルダで示す |
| `presentationYear` | 資料 | 4桁の西暦年、または `null` | 発表年。Driveへの登録日・更新日とは別 |
| `slideRole` | ページ | `title`, `background`, `related_work`, `objective`, `method`, `experiment`, `result`, `conclusion`, `other`, `null` | そのページの主な役割。複数の話題は既存のタグで補う |

`null` は未設定・不明を表し、`other` は確認したが選択肢に当てはまらない場合に使う。既存資料には `null` を適用し、カテゴリや役割をフォルダ名・見出しだけから確定しない。検索では指定値に完全一致させ、条件を指定しなければ未設定の資料・ページも含める。区分と役割の候補はBackendとFrontendで同じ定義を使い、追加時にデータとUIを同時に更新する。

画面では `paper_reading` を「論文読み会」、`research_presentation` を「研究発表」と表示する。`slideRole` もコード値とは別に日本語の表示名を持たせる。

タイトル・著者・区分・発表年は資料の属性、スライドの役割・タグはページの属性とする。著者はDriveの所有者やアップロード者から推測しない。ファイル名やタイトルページから候補を得る場合も、利用者が確認・修正できるようにする。AI解析を追加する際は、推定した項目ごとに由来（入力・ファイル抽出・Drive・モデル）と確認状態を保存し、モデル名と版も記録する。推定値を人間が確認した値と区別する。

## Drive由来の資料（追加予定・Issue #6）

Drive上のPDFは取り込み時にライブラリの保存領域へコピーし、通常のPDFと同じページ画像・検索データを生成する。`format` は `pdf`、`GET /api/documents/{documentId}/source` が返すのも取り込んだPDFである。変換前のPPTXがDriveに存在するとしても、自動的に元PPTXと対応付けたり、PPTXをダウンロード可能と表示したりしない。

資料には登録経路を表す `origin.kind`（`upload` / `google_drive`）を持たせる。Drive由来の場合の内部データ例は `{"kind":"google_drive","driveFileId":"...","driveModifiedTime":"...","driveFolders":[{"id":"...","name":"論文読み会"}]}` とする。既存の `folderPath[]` はフォルダ名の表示・検索に使い、DriveのIDは同名フォルダの識別と再取り込み判定に使う。階層の一部を取得できない場合は、分かる範囲だけ表示し、完全な階層を推測しない。Driveの参照リンクを示す場合も、その利用者にDrive側の閲覧権限があるとは限らない。

初回の単一ファイル取り込みではDriveファイルIDで既存資料を確認し、同じファイルの重複登録を避ける。自動同期と、Drive上で更新されたPDFの再取り込み・ページIDの扱いは別途設計する。Driveの更新時刻は発表年の代わりにしない。Driveの閲覧権限はライブラリ内のコピーに引き継がれないため、取り込み前に共有ライブラリの利用者全員へ見せてよい資料か確認する。[Google Driveのファイル属性](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)と[共有権限](https://developers.google.com/workspace/drive/api/guides/manage-sharing)を参照する。

## PDF/PPTX登録情報

現在の登録APIはファイルに加え、`title`、`authors[]`、`folderPath[]` を受け取る。`title` は必須、著者とフォルダ階層は任意とする。サーバー側でファイル形式を検証し、処理状態と保存先を記録する。ページ画像・見出し・概要・ページ数は取込処理の結果として追加する。`category` と `presentationYear` は任意の登録情報として追加する予定で、既存資料も後から修正できるようにする。登録日時とページ全文の保存は今後の拡張項目とする。

## エージェント・Skillからの利用

将来、エージェント用SkillなどがAPIを通じてページを検索し、スライド作成の参考資料を選べるようにする。特定のSkill専用の項目を設けず、人間向け画面とエージェントが共通の資料・ページメタデータを利用する。検索結果は候補選択に必要な概要を返し、詳しい表現・構成情報は選択したページについて取得する。元資料の出典、共有・再利用の条件も確認できる形を目指す。

フェーズ1では安定したページID、資料ID、ページ番号、見出し・概要・タグ、元フォルダ階層を保持する。内容や見た目に基づく選択に必要な情報は、後から追加する項目として扱う。

## 後から追加する情報

- Driveの自動同期・更新検知と再取り込み履歴
- 抽出文字列を利用した高度な検索、図の種類・レイアウト・配色などの視覚的な特徴
- 元資料の参照先、共有範囲、再利用条件
- ページIDに紐づくEmbedding、使用モデルとバージョン、生成日時

Embeddingはページの基本レコードと分けた派生データとして扱う。同じページに異なるモデルの結果を持てるようにし、検索基盤の製品は意味検索を実装する段階で選ぶ。
