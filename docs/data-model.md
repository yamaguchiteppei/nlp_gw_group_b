# データ設計

検索・表示の単位は**ページ**、出典と登録の単位は**資料**とする。APIのJSONでは以下の名前を使う。開発用モックも同じ形にする。

| 単位 | 主な項目 | 説明 |
| --- | --- | --- |
| 資料 `Document` | `id`, `title`, `authors[]`, `fileName`, `format`, `folderPath[]` | 元ファイルと全ページに共通する情報 |
| ページ `Page` | `id`, `documentId`, `pageNumber`, `heading`, `summary`, `tags[]`, `previewUrl` | 検索結果・詳細表示の単位 |

`id` はファイル名やページ番号から作らない安定した識別子とする。`pageNumber` は1始まり。`format` は `pdf` または `pptx`。著者が不明なら空配列、見出し・概要が不明なら空文字列を使う。著者は資料に、役割を表すタグはページに付ける。

`folderPath` は `['論文読み会', '2025']` のように上位から並ぶ出典情報である。フォルダ階層による絞り込みに使うが、フォルダ名をページのタグへ自動変換しない。Drive連携時は表示用の階層に加え、元フォルダを識別するIDを保持する方法を検討する。

## PDF/PPTX登録情報

登録時はファイルに加え、`title`、`authors[]`、`folderPath[]` を受け取る。`title` は必須、著者とフォルダ階層は任意とする。サーバー側でファイル形式を検証し、登録日時、処理状態、保存先を記録する。ページ画像・抽出文字列・ページ数は取込処理の結果として追加する。PDFと元PPTXが同じ発表の別形式だと分かる場合の関連付け方法は、実ファイルを扱う段階で決める。

## 後から追加する情報

- 手入力、ファイルからの抽出、AI候補を区別できるメタデータの由来と確認状態
- Driveのファイル・フォルダ識別子、更新時刻、同期状態
- ページの抽出文字列、図の種類や配色などの視覚的な特徴
- ページIDに紐づくEmbedding、使用モデルとバージョン、生成日時

Embeddingはページの基本レコードと分けた派生データとして扱う。同じページに異なるモデルの結果を持てるようにし、検索基盤の製品は意味検索を実装する段階で選ぶ。
