# 開発への参加方法

小規模なチームでGitHub Flowを使う。機能・不具合・設計はIssueに目的と完了条件を書き、作業ブランチからPRを作る。PRには変更内容、関連Issue、確認方法と結果を記載し、少なくとも1人がレビューする。

## ブランチとPR

- `main`を安定ブランチとし、作業はIssue単位のブランチで行う。
- ブランチ名の例：`feature/12-slide-search`、`docs/18-api-spec`。
- 仕様変更を含むPRでは[基本設計](architecture.md)、[データ設計](data-model.md)、[API仕様](api.md)の該当箇所も更新する。
- UI変更ではスクリーンショットを添える。レビュー後、導入済みのCIが成功してからマージする。

## テストとCI

最初の実装PRで、ローカルとGitHub Actionsの両方で実行できるチェックを追加する。バックエンドはPythonのLint・テスト、フロントエンドはLint・型チェック・ビルドを基本とする。具体的なコマンドは依存関係と一緒に固定する。

検索では、日本語の文字列、タグ、親フォルダによる絞り込み、複数条件、該当なし、存在しないページIDを確認する。画面では一覧・詳細とエラー時の表示を確認する。登録ではPDF/PPTXの形式検証、取込失敗、永続化を確認する。

Swagger UIでAPIを手動確認できるようにするが、期待結果の検証は自動テストでも行う。CIの必須チェック設定は、ワークフローが安定してから行う。

## 資料の扱い

秘密情報、未公開資料、個人情報を許可なくリポジトリに追加しない。サンプルには公開・共有が許可されたファイルか架空のデータを使う。
