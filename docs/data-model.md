# データ設計

検索・表示の単位は**ページ**、出典と登録の単位は**資料**とする。ページは人間向け画面とエージェントに共通の資産として扱う。APIのJSONでは以下の名前を使う。

| 単位 | 主な項目 | 説明 |
| --- | --- | --- |
| 資料 `Document` | `id`, `title`, `authors[]`, `fileName`, `format`, `folderPath[]`。将来、`category`, `presentationYear` も追加 | 元ファイルと全ページに共通する情報 |
| ページ `Page` | `id`, `documentId`, `pageNumber`, `heading`, `summary`, `tags[]`, `previewUrl` | 検索結果・詳細表示の単位。API応答では `document` に資料情報も含める |

`Document.id` は登録したPDF/PPTXの資料全体のID、`Page.id` は1ページのIDとする。どちらもファイル名やページ番号から作らない安定した識別子とする。`Page.documentId` で資料全体に紐づけ、`pageNumber` はその資料内で1始まりとする。`format` は `pdf` または `pptx`。著者が不明なら空配列、見出し・概要が不明なら空文字列を使う。著者は資料に、役割を表すタグはページに付ける。

ページは `documentId` で資料に紐づく。APIの `Page` 応答には、資料情報を `document` として含め、`document.id` と `documentId` を一致させる。一覧・検索では候補選択用の `PageSummary` を返す。取込直後のページのタグは空配列とし、後からページ単位で付与・修正する。

メタデータは用途に応じて次の3種類に整理する。

| 種類 | 主な情報 | 用途 |
| --- | --- | --- |
| 基本情報 | ID、ページ番号、見出し、概要、タグ、プレビュー、資料タイトル・著者・元フォルダ | 一覧・検索・詳細表示 |
| 意味・表現情報 | 発表内での役割、説明の流れ、内容・図の種類、レイアウト、強調点 | 詳細な検索、エージェントによる参考例の選択 |
| 技術情報 | 元ファイル、抽出文字列・図形情報、Embedding、解析モデルと版 | 取込処理、検索処理、高度な参照 |

Embeddingは検索の内部処理に用い、生ベクトルは通常の検索・詳細APIで返さない。元ファイルは資料に紐づき、プレビューはページに紐づく。

`folderPath` は `['論文読み会', '2025']` のように上位から並ぶ出典情報である。フォルダ階層による絞り込みに使うが、フォルダ名をページのタグへ自動変換しない。Drive連携時は表示用の階層に加え、元フォルダを識別するIDを保持する方法を検討する。

初期の資料一覧は取得済みのページを `documentId` でまとめて構成する。資料詳細では `GET /api/documents/{documentId}/pages` で全ページを `pageNumber` 順に取得する。ページ数はそのAPIの `total` を使い、代表画像には既存ページのプレビューを参照する。資料区分 `category` と発表年 `presentationYear` を利用する段階で `Document` に追加し、不明な値を許容する。フォルダ階層だけから確定値を推測しない。

## PDF/PPTX登録情報

登録時はファイルに加え、`title`、`authors[]`、`folderPath[]` を受け取る。`title` は必須、著者とフォルダ階層は任意とする。サーバー側でファイル形式を検証し、処理状態と保存先を記録する。ページ画像・見出し・概要・ページ数は取込処理の結果として追加する。登録日時とページ全文の保存は今後の拡張項目とする。PDFと元PPTXが同じ発表の別形式だと分かる場合の関連付け方法は、実ファイルを扱う段階で決める。

## エージェント・Skillからの利用

将来、エージェント用SkillなどがAPIを通じてページを検索し、スライド作成の参考資料を選べるようにする。特定のSkill専用の項目を設けず、人間向け画面とエージェントが共通の資料・ページメタデータを利用する。検索結果は候補選択に必要な概要を返し、詳しい表現・構成情報は選択したページについて取得する。元資料の出典、共有・再利用の条件も確認できる形を目指す。

フェーズ1では安定したページID、資料ID、ページ番号、見出し・概要・タグ、元フォルダ階層を保持する。内容や見た目に基づく選択に必要な情報は、後から追加する項目として扱う。

## 後から追加する情報

- 手入力、ファイルからの抽出、AI候補を区別できるメタデータの由来と確認状態
- Driveのファイル・フォルダ識別子、更新時刻、同期状態
- 抽出文字列を利用した高度な検索、発表内での役割、図の種類・レイアウト・配色などの視覚的な特徴
- 元資料の参照先、共有範囲、再利用条件
- ページIDに紐づくEmbedding、使用モデルとバージョン、生成日時

Embeddingはページの基本レコードと分けた派生データとして扱う。同じページに異なるモデルの結果を持てるようにし、検索基盤の製品は意味検索を実装する段階で選ぶ。

意味・表現情報には項目ごとに値の由来と確認状態を持たせる。例えばページ番号はファイルから確定できる値、スライドの役割はモデルによる推定または人間が修正した値として区別する。解析に用いるモデル名とバージョンも記録し、推定結果を確定情報として扱わない。
